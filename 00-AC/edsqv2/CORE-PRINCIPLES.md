# AC Platform 核心原则

> **不可动摇的铁律**

---

## 核心原则

```
AC is a read-only auditor over Trae workspace.

It observes, reports, never modifies.

整个开发环境：Trae 写代码，AC 盯着，你决策。
```

---

## 原则解释

### 为什么 AC 不能修改 Trae 的代码？

1. **公信力问题**：AC 自己改代码，然后自己审计，形成检查-修改循环
2. **锚点破坏**：AC 的核心价值是"不可销毁的痕迹"——如果 AC 自己修改，痕迹就不存在了
3. **责任边界**：修正动作必须由你（用户）或 Trae 在看过告警后手动触发

### AC 的职责边界

| AC 可以做 | AC 不能做 |
|-----------|-----------|
| 观察 Trae 工作目录 | 修改 Trae 工作目录 |
| 报告问题（文件+行号） | 自动调用 Edit 工具修正 |
| 推送治理告警 | 自动修改代码 |
| 审计代码质量 | 执行代码修改 |

## 架构角色

```
┌─────────────────────────────────────────────────────────────────┐
│                        Trae (你)                                │
│                     写代码 / 决策 / 修正                         │
└─────────────────────────────────────────────────────────────────┘
                              ▲
                              │ 告警报告（只读）
                              │
┌─────────────────────────────────────────────────────────────────┐
│                      AC Platform                                │
│                   观察 / 报告 / 审计                             │
│                                                                 │
│   - File Watch: 监听文件变更                                     │
│   - Governance: 执行 G0-G3 治理                                  │
│   - Alert: 推送问题报告                                         │
│                                                                 │
│   AC NEVER MODIFIES Trae workspace.                             │
└─────────────────────────────────────────────────────────────────┘
```

---

## Phase A & B 原则

### Phase A：REST 先通
- AC Server 接收请求，返回结构化 JSON
- Trae 通过 `ac_client.py` 调用
- **原则**：AC 只返回审计结果，不执行修改

### Phase B：WebSocket + File Watch
- AC 主动推送治理告警
- Trae 消费诊断信息
- **原则**：告警推送 = 观察报告，修正由你手动触发

---

## 错误处理原则

1. **AC 失败**：返回错误，不修改任何内容
2. **治理失败**：返回告警，不自动修正
3. **超时**：返回 504，不阻塞 Trae

# 架构风险复盘 · 2026-05-13/14

> 按今天发现的时间线，以绝对颗粒度记录所有架构级问题。
> 每个问题包含发现场景、根因、工业对应缺陷、当前影响。

---

## P0-1 · 运行目录与仓库分裂（双份代码）

- **发现**：`{USER_HOME}\ac\` 是运行目录，`HERMES-DATE\HERMES-DATE\` 是 git 仓库。`core.py` dispatch 改造、`validator.py` L2 修复只改了一边，测试脚本在两处手动复制。
- **根因**：没有明确的源码主目录，运行与开发环境未统一，无自动同步机制。
- **缺陷类型**：配置漂移 / 环境不一致
- **后果**：从不同目录启动会执行不同版本的代码，问题极难排查，已构成事实上的"分裂脑"。

## P0-2 · governance/__init__.py 顶层硬依赖阻塞测试

- **发现**：`governance/__init__.py` 第 3 行 `from ac.governance.checker import ...` 导致任何 `import governance` 都触发 `ac` 包上下文依赖，测试全部需绕过。
- **根因**：包初始化时执行了重依赖导入，违反"导入应无副作用"原则。
- **缺陷类型**：模块耦合 / 可测试性破坏
- **后果**：测试无法独立运行，必须使用 `exec()` 等绕过手段，新人或 CI 环境会直接失败。

## P0-3 · dispatch 到 orchestrator 升级通道不存在（escalate 虚构）

- **发现**：第三关测试中添加了 `escalate` 字段，但 `orchestrator` 未监听，`stream_router.py` 仅为设计文档，`unclassified` 后的处理逻辑缺失。
- **根因**：契约未实现，测试中的字段是"愿望"，而非真契约。
- **缺陷类型**：死代码 / 未实现接口
- **后果**：无法分类的消息被静默丢弃，生产环境会直接丢失业务请求，且测试通过假象掩盖风险。

## P0-4 · 对话端写文件绕过 AC 治理管道（G3 真空）

- **发现**：对话端通过 `Write/Edit` 直接操作文件系统，全程不经 G0-G3，不触发 `governance/pipeline.py`。
- **根因**：治理管道与对话端工具链没有集成，治理仅守卫 CLI/Web 入口。
- **缺陷类型**：权限绕过 / 治理盲区
- **后果**：文件内容可含幻觉、矛盾，无任何自动检查，当前唯一防线是你事后手动调用 `annotate`。

## P1-1 · 真值知识库与核心链路完全断裂

- **发现**：`dispatch()` 不查询 `ac_truth` 或 `ChromaDB`；`orchestrator VERIFY phase` 不对比已有事实；`HallucinationAuditor` 未集成进 G3。知识入库后不参与任何决策。
- **根因**：知识库被设计为被动存储，没有暴露为统一知识服务（KnowledgeService），各模块各自为政。
- **缺陷类型**：数据孤岛 / 知识未激活
- **后果**：知识库投入产出比为零，验证无锚点，幻觉检测无事实参照。

### 入库链路 · 绝对颗粒度展开

```
输入 → store_truth() → validate_truth() L0/L2/L5 → ac_truth
  │                                                     │
  │                                          (缺) dispatch 不读
  │                                          (缺) orchestrator 不查
  │                                          (缺) hallucination 不对比
  │                                                     │
  │  ┌─ 入库判定树 ───────────────────────────────────┐ │
  │  │  PASS + L5 → verified=1, 写 truth               │ │
  │  │  PASS + L2 → verified=0, 写 truth, 标记待审     │ │
  │  │  FAIL 重复 → 不写, 记录日志                      │ │
  │  │  FAIL 矛盾 → 不写, 触发 case_center 告警        │ │
  │  └────────────────────────────────────────────────┘ │
  │                                                     │
  │  ┌─ 入库后的消费链路（全部缺失） ─────────────────┐ │
  │  │  dispatch 不查 truth → 知识不参与调度决策        │ │
  │  │  orchestrator 不查 truth → 验证无锚点            │ │
  │  │  hallucination 不查 truth → 检测无事实参照        │ │
  │  │  case_center 不被 dispatch 调用 → 失败经验不复用 │ │
  │  └────────────────────────────────────────────────┘ │
```

### 绝对真值表 · 入库与删除规则

**ac_truth 表的当前约束：**

| 规则 | 实现状态 | 说明 |
|------|----------|------|
| 入库需经 validate_truth() | ✅ guard.py store_truth() 强制 | 唯一通道，禁止直接 INSERT |
| L5 级才标记 verified=1 | ✅ validator.py 评分公式 | score≥0.85 |
| 重复内容检测 | 🟡 L2 check 已修复 | 字符级 Jaccard + n-gram |
| 矛盾内容拦截 | 🟡 L2 check 已修复 | 锚点库 + 已有真值比对 |
| **绝对真值不可删除** | ❌ 未实现 | 当前允许 DELETE / DROP |
| 软删除（标记不物理删除） | ❌ 未实现 | 无 deleted_at 字段 |
| 版本追溯（修改留痕） | ❌ 未实现 | 无 version 链 |
| 置信度衰减（TTL） | ❌ 未实现 | 180 天未验证 → L5→L2→L0 |
| 回滚机制（误写入可撤销） | ❌ 未实现 | 无 UNDO / 快照 |

**绝对真值的核心原则（建议）：**

```
1. 一条真值一旦验证为 L5 → 永久保留，不可物理删除
2. 修改必须走新版本（version +1），旧版本不可覆盖
3. 误写入 → 标记 deleted_at 软删除，保留审计轨迹
4. 数据库 schema 版本和真值版本分离管理
5. 任何 DDL 操作必须走 migration 脚本，禁止 ALTER TABLE
```

当前 `ac_platform.db` 的 migration 版本是 v2，使用 `db_migration.py` 管理。但 `ac_truth` 表内没有 `version`、`deleted_at`、`superseded_by` 等字段，无法支持真值级别的版本追溯。

## P1-2 · G3 治理管道缺少 HallucinationAuditor

- **发现**：`governance/pipeline.py` 的 checker 列表只有 5 个，`HallucinationAuditor` 仅在测试中单独运行。
- **根因**：开发完未集成，管道未更新。
- **缺陷类型**：防御链缺失
- **后果**：输出可通过所有检查但仍包含虚构内容，治理管道对幻觉"透明"。

## P1-3 · SubAgent 状态机与 AC Platform 完全隔离

- **发现**：SubAgent 有自己的状态机、L1-L3 验证、模型路由，与 AC 的 Dispatch/Orchestrator/G3 形成两套平行的"大脑"。没有触发关系，没有结果合并。
- **根因**：两系统各自独立开发，无统一调度中枢（Central Scheduler）或事件总线（AC Bus）。
- **缺陷类型**：双头架构 / 能力重叠
- **后果**：同一请求可能得到两种处理方式和两种结果，调试需跨两个系统的日志，审计线索断裂。

## P1-4 · 上下文治理结果随 session 消失（不可持久化）

- **发现**：对话端的 C1-C4 检查（上下文一致性、工具选择等）发现的问题仅存在于当前对话，session 结束后永久丢失。
- **根因**：缺乏治理快照机制，无法写入 `governance_events` 或 `case_center`。
- **缺陷类型**：组织记忆丧失
- **后果**：架构发现无法累积为系统知识，每次 session 都是从零开始的"失忆症"。

## P2-1 · 入口 Gate 缺失（无输入分类/去重/频率限制）

- **发现**：所有入口（CLI/Web/对话）无统一输入治理，无复杂度预判、无去重、无速率限制。
- **根因**：L0 只做了编码清洗，未向上抽象出入口治理层。
- **缺陷类型**：无防护入口
- **后果**：可被重复提交压垮，恶意或错误请求直通核心逻辑。

## P2-2 · 自动化 CI/CD 完全缺失

- **发现**：无 GitHub Actions，测试靠手动 `run_tests.py`，部署靠手动复制到 GitHub Pages，无自动回滚，无依赖漏洞扫描。
- **根因**：项目初期未引入 CI/CD，一直依赖人工。
- **缺陷类型**：工程代谢缺失
- **后果**：任何一次 push 都可能引入未检测的破坏，部署完全依赖操作者记忆，无版本追溯。

## P2-3 · 多 CLT 接入架构缺少持久化队列与死锁保护

- **发现**：队列使用内存 `asyncio.Queue`，资源锁无 TTL，无心跳联动，进程重启丢消息且可能死锁。
- **根因**：当前仍是单机脚本思维，未按分布式系统设计。
- **缺陷类型**：可靠性缺失
- **后果**：Server 模式一上线，进程崩溃或重启会直接丢请求、锁资源永久占用。

## P2-4 · 模块间信息传递缺少协议与健康检查

- **发现**：对话端与 AC 之间通过直接 `import` 调用（绕过治理），SubAgent 与 AC 无通信，无跨模块心跳，无统一健康检查。
- **根因**：系统无事件总线和统一 API 规范。
- **缺陷类型**：集成脆弱
- **后果**：任何模块离线不会被自动发现，故障定位依赖人工逐一排查。

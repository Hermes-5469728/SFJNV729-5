## ADR-001 · 2026-05-01 · 六层防御非三层非十层

**背景**: LLM输出含幻觉。防御可以轻(1-2层)或重(10+层)。

**选项**:
- A: 轻量防御(正则+关键词·2层)
- B: 六层纵深(L1-L6·当前)
- C: 全量防御(10+层·加模型蒸馏、对抗训练等)

**选择**: B

**理由**: 两层太薄——正则拦不住自信的幻觉。十层太重——学生项目资源不够。六层在深度和可维护性之间取中点。L2 NLI辩论是"未来预留"——当前部分mock，条件成熟后激活。

**后果**: 防御层增加响应延迟。L2的mock标记给了外部诚实信号。

## ADR-002 · 2026-05-01 · File-as-Code(.txt)非SQLite

**背景**: 药物数据库需要持久化。选项：文本文件 vs SQLite vs 外部数据库。

**选项**:
- A: SQLite(本地·有schema·可索引)
- B: .txt文件(扁平·人类可读·专家可直接编辑)
- C: PostgreSQL/MySQL(外部服务·需要运维)

**选择**: B

**理由**: 三甲医院场景——药房主任需要能直接打开文件查看和修改数据。SQLite需要额外工具。.txt可以git diff、可以打印、可以手写补充。零学习成本。31药·21相互作用的数据量不需要索引。

**后果**: 无schema约束——格式错误需要人工发现。无事务——并发写入可能覆盖。数据库变大后需迁移。当前规模不触发这些问题。

## ADR-003 · 2026-05-03 · Gaia统一管道非每入口独立

**背景**: 幻觉防御最初耦合在agent-runner.py内部。copilot_app和medical_app各自为空。

**选项**:
- A: 每个入口独立实现防御(复制粘贴)
- B: 统一管道(GaiaDefensePipeline)·所有入口调用同一对象

**选择**: B

**理由**: 三个入口如果不走同一管道，防御行为不一致——一个拦截的输入在另一个可能通过。管道可独立测试、独立版本管理。入口只负责调用。

**后果**: 管道导入需要在多处sys.path处理。L2占位符需明确标记[NLI_DEBATE:SKIPPED]。

## ADR-004 · 2026-05-03 · Streamlit非React/Vue

**背景**: 需要GUI。选项：Web框架 vs Python原生。

**选项**:
- A: React/Vue(专业前端·生态丰富)
- B: Streamlit(纯Python·快速原型)
- C: Tkinter(纯桌面·无浏览器)

**选择**: B

**理由**: 零前端基础。Streamlit一个Python文件跑全栈。学习成本趋近零。医疗场景不需要高交互——表格、输入框、展开面板就够了。240行DADS证明了可行性。

**后果**: 无法自定义CSS/动画。大规模部署不适合。但三甲内网场景——单人/小团队使用——完全够用。

## ADR-005 · 2026-05-03 · 强制幻觉标注(L5)

**背景**: AI生成的输出应该标注风险。

**选项**:
- A: 不标注(默认可信)
- B: 隐式标注(小字·底部·容易忽略)
- C: 强制显式标注(中英双语·底部·不可移除)

**选择**: C

**理由**: 利托那韦晶型事件——一个真实失误改了全球药品审批标准。医疗场景下，不标注AI风险 = 隐瞒已知缺陷。L5强制标注是系统的最低安全承诺。即使UI是AI生成的——也必须说"我是AI生成的"。

**后果**: 每个界面底部都有两行标注。对用户视觉上有干扰。但设计上不可移除——这是底线。

## ADR-006 · 2026-05-03 · DeepSeek API非GPT/Claude

**背景**: 需要LLM后端。

**选项**:
- A: GPT-4(最强·最贵)
- B: Claude(长上下文·中等价格)
- C: DeepSeek(国产·便宜·可用)

**选择**: C

**理由**: 学生预算。¥72/月跑756万Token。GPT-4同等量级¥500+。DeepSeek V3足够日常——V4 Pro留给生产。幻觉率虽然比GPT高——但Gaia六层防御正好补这个。成本敏感+防御完备=最优组合。

**后果**: DeepSeek幻觉率高于GPT。但系统设计就是默认不信任任何LLM输出——模型的弱点被架构补偿了。

## ADR-007 · 2026-05-04 · 医疗第一垂直非法律/金融

**背景**: 通用决策引擎需要第一个落地场景。

**选项**:
- A: 医疗(有临床背景·高容错需求)
- B: 法律(无背景·类似高容错)
- C: 金融(无背景·容错需求较低)

**选择**: A

**理由**: 自己的专业领域。知道痛点在哪。有真实病历可验证。医疗容错为零——如果系统在医疗跑通了，在其他领域降低标准即可。反之则不成立。

**后果**: 医疗术语、指南更新、药物库维护都是长期工作。但这是护城河——别人进不来。

## ADR-008 · 2026-05-04 · 正则+本地表非LLM提取药物

**背景**: 从临床笔记提取药物信息。

**选项**:
- A: LLM提取(灵活·可能幻觉)
- B: 纯正则+本地表(确定·覆盖有限)
- C: 混合(正则优先·LLM补充)

**选择**: B

**理由**: 三甲医院要求输出可审计。LLM提取的"阿司匹林"——来源是模型的参数权重——无法溯源。正则匹配的"阿司匹林5mg"——来源是drugs.txt第3行——可以溯源。确定性>覆盖率。宁可不提取，不可提取错。

**后果**: 非结构化文本(手写笔记·口语化描述)会漏掉。多词药名(valproic acid)只匹配第一个词。覆盖31种药——需要持续扩充数据库。

## ADR-009 · 2026-05-05 · 暂不容器化(Docker)

**背景**: 部署需要环境一致性。

**选项**:
- A: Docker(标准·可复制)
- B: SETUP.md + requirements.txt(手动·简单)

**选择**: B

**理由**: 当前阶段——单人开发·单机运行——Docker增加认知负载而不增加实际价值。学员/药师双击DADS.bat就能跑不需要Docker Desktop。等需要团队协作或多机部署时再容器化。

**后果**: 换电脑需要手动装环境。但SETUP.md已经写了完整步骤。这是有意识的延迟——不是遗漏。

## ADR-010 · 2026-05-05 · 宪法为公理非定理

**背景**: 架构宪法6条——它们本身的真值无法被系统验证。

**选项**:
- A: 假装它们是已验证的事实
- B: 标注为[AXIOM]——承认它们是公理·不需要证明

**选择**: B

**理由**: 自指悖论——宪法由LLM生成，按L4规则会被排除。公理化标签是唯一诚实的出口。公理可以被辩论、被修改、被推翻——但不能被自己的规则杀死。

**后果**: 外部攻击可以质疑宪法本身。但如果有人提出修改宪法——走人工审批，不是自动采纳。这是设计上的诚实——不是漏洞。

## ADR-011 · 2026-05-05 · 常态化高频更新(txt数据库非模型训练)

**背景**: 指南更新频繁(NCCN每1-3月)，药物相互作用新发现不断。系统不使用模型微调，但.txt数据库仍然会"漂移"——旧数据 ≠ 当前临床实践。

**选项**:
- A: 静态数据库(手动不定期更新)
- B: 专家定期审核(每周/每月·人工维护)
- C: 自动化更新(从FDA/指南网站抓取——需要网络)

**选择**: B（当前）→ 逐步向A+C混合过渡

**理由**: 当前阶段——专家定期审核最可行。31种药、21组相互作用的规模人工可维护。L6指南时效窗口(90天)作为阈值——超时未更新标记[GUIDELINE:STALE]。未来：医院内网的中央药库可以直接映射到drugs.txt。

**后果**: 数据库需要专人维护——药房主任或临床药师。没有自动化更新意味着更新频率取决于人的时间。但这也意味着每次更新都是人类专家验证过的——零幻觉注入。AI生成的药物数据不进入数据库。

## ADR-013 · 2026-05-05 · 决策优先于迭代

**背景**: 凌晨思维过度迭代导致睡眠受损。第二天决策质量下降形成负反馈循环。

**选项**:
- A: 随时迭代(随时改代码)
- B: 时间窗口(只在高精力时段迭代)
- C: 全停(暂停所有迭代·只对话)

**选择**: B

**理由**: 精神科就诊记录(2026-05-05): "焦虑状态·失眠"。架构迭代是认知负载的出口——但不加时间窗口会反噬。脑力低谷不做架构决策。具体规则: 22:00-08:00不写代码。疲劳时只做事务——(整理文档/读理论/对话)。

**后果**: 夜间想法写入BRAINDUMP.md——第二天复盘。这个ADR本身是在凌晨写的——但它的内容就是在约束凌晨行为。这是自指——但它有效。

## ADR-014 · 2026-05-05 · 未来架构演进路线(休眠决策·条件激活)

**背景**: 当前单机单人架构。未来需要多科室、多医院、多租户扩展。

**当前不需要·未来需要的**:

| 领域 | 当前决策 | 触发条件 | 未来方向 |
|------|---------|---------|---------|
| 多租户 | 单用户·游客登录 | 医院部署·>5用户 | 每租户独立.txt → 共享表+租户过滤 → 独立DB |
| 容器化 | SETUP.md手动 | 团队协作·多机 | Docker → docker-compose → k8s |
| 消息队列 | File-as-Code(INBOX/OUTBOX) | 实时性需求·>3服务 | Redis/RabbitMQ |
| 微服务 | 单进程 Streamlit | 多科室独立部署 | BFF + service-per-domain |
| 数据隔离 | 单文件 drugs.txt | 跨医院数据合规 | 每租户独立存储+GDPR区域路由 |
| 测试流水线 | 手动 `python test.py` | 团队·持续集成 | pytest + GitHub Actions + 契约测试 |
| Service Mesh | 不需要 | >10微服务 | 暂时不需要 |
| 事件溯源 | 不需要 | 审计合规强制要求 | audit.jsonl → EventStore |
| DDoS防护 | 127.0.0.1单机·无公网暴露 | 医院内网部署·对外开放端口 | nginx rate-limit → fail2ban → 云清洗(阿里云高防) |
| AI驱动的攻击 | 不适用(无公网) | 公网部署后 | 流量指纹+异常检测+自动熔断 |

**选择**: 不提前实现。每个工具只在触发条件满足时激活。休眠协议模式: 写好了是什么、为什么、何时激活——但不建。

**理由**: 20岁学生做一个可能永远不用多租户的项目——做多租户就是过度设计。但知道"如果医院部署了要改什么"就是架构意识。ADR记录这个意识。

**后果**: 当前代码堆了单机假设。迁移到多机需要重构数据层。但有这份 ADR——以后的人知道当时为什么这么选、改的时候改哪里。这比代码注释更有价值。

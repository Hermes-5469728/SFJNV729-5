# 意图卡 · 优雅降级与熔断

## 模块名
`fallback` — 全模块超时熔断 + 优雅降级链

## 目标
为 AC 系统的每一个外部依赖（API 调用、数据库连接、SubAgent 执行）配备超时熔断器和降级路径，确保任何单点故障不会导致全系统崩溃。

## 背景
- **宪法规则**: 宪法铁律第 5 条 — AC 是只读审计者，不自动修改用户代码。但当前系统在 API 超时/DB 锁死/内存溢出时无降级策略，直接抛异常甚至静默 hang
- **猎鬼发现**: 架构审计 (2026-05-13) 第 11 项 — 队列不可靠。内存队列无 TTL，进程重启丢消息+死锁。`ac_circuit_breaker` 表已有 511 条熔断记录，证明熔断器在运行，但仅覆盖个别模块
- **为什么需要**: 当前 `deepseek_free.py` 调用 DeepSeek API 无超时；`chromadb` 向量检索无超时；SubAgent 执行无超时。任何一个外部依赖卡死，`jarvis_core.chat()` 就永久阻塞。多 AI 同时调用时可能形成雪崩

## 输入
| 参数 | 类型 | 说明 |
|------|------|------|
| `callable` | `Callable` | 需要被熔断器包裹的函数 |
| `timeout_ms` | `int` | 超时时间（毫秒），默认 30000 |
| `fallback_fn` | `Callable \| None` | 降级函数，超时时调用。None 则返回默认降级结果 |
| `circuit_name` | `str` | 熔断器名称（用于写入 ac_circuit_breaker 表） |
| `max_failures` | `int` | 连续失败多少次后熔断开路，默认 3 |
| `recovery_ms` | `int` | 熔断后多久尝试恢复（半开），默认 60000 |

## 输出
```python
{
    "result": Any | None,        # 正常结果或降级结果
    "status": str,               # ok / degraded / timeout / circuit_open
    "elapsed_ms": int,           # 实际耗时
    "circuit_state": str,        # closed / open / half_open
    "retry_count": int,          # 本次调用的重试次数
    "fallback_used": bool,       # 是否触发了降级
}
```

## 关键约束
1. **必须写入 `ac_circuit_breaker`** — 每次熔断/恢复/降级事件写入数据库，与已有 511 条记录格式一致
2. **必须对接 `governance_events`** — 降级事件写入 (event_type=`fallback_degraded`)
3. **降级链必须显式声明** — 每个模块的降级路径不可隐含，必须在初始化时注册：`deepseek_api → local_cache → empty_response`
4. **超时不可无限重试** — 最多重试 2 次，指数退避（1s, 2s, 4s）
5. **熔断器必须是装饰器** — `@circuit_breaker(timeout=30000, fallback=local_cache)` 语法，零侵入接入现有函数
6. **不吞异常** — 降级后仍需记录原始异常到日志，不能静默丢弃

## 已知难点
1. **SQLite 写锁争用** — 多个熔断器同时写入 `ac_circuit_breaker` 表时可能触发 SQLite 写锁。需要 WAL 模式 + 批量写入
2. **降级路径的降级** — 如果 fallback_fn 本身也超时，需要终极兜底（硬编码的空响应）。三层降级链: primary → fallback → ultimate_empty
3. **ChromaDB 超时不可控** — `chromadb` 库的 `query()` 方法不接受 timeout 参数。需要线程级别的强制中断（`threading.Timer` 或 `asyncio.wait_for`）
4. **与现有熔断器的兼容** — `ac_circuit_breaker` 表已有 511 条记录，当前写入格式未知。需要先逆向现有熔断逻辑，保持 schema 兼容
